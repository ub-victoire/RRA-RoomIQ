### Stage gate rules

- Work proceeds one requirement at a time; no later requirement is started until the current requirement passes its focused test, the identity suite, and the full Stage 1/reactor regression required by the gate.
- If a requirement or implementation reveals a possible ERD change, present the proposed change and wait for user approval before editing the ERD.
- Keep persistence ownership service-local; cross-service references remain identifiers plus API/event integration, never shared entities or cross-service database writes.
- Keep statuses evidence-based: a scaffold, shared default, or partial workflow is not marked complete as a domain requirement.
- After implementation and verification, synchronize this roadmap, service documentation, SRS/ERD traceability, and the API/Postman contract before asking for the next stage/requirement approval.

### Stage 5 implementation constraints

- Scheduling owns working calendars, day windows, holidays, closures, recurrence rules, scheduling validation, and availability calculation.
- Room continues to own maintenance periods and room status/rules. Booking owns confirmed reservations and the authoritative overlap constraint.
- Booking's occupied interval includes the configured five-minute release buffer; a read-only availability result is never the final double-booking barrier.
- `POST /api/v1/availability/search` returns continuous candidate intervals (not a generated slot grid) with explicit `Instant` boundaries and calendar timezone. For recurrence, each returned window represents an individual RRULE occurrence; it does not certify a common interval across the full recurrence series. Booking must validate the complete recurrence before confirmation.
- The search horizon is at most 31 days and at most 5,000 candidate windows. An oversized search returns an error rather than partial/truncated availability.
- The internal Booking snapshot contract is versioned as `v1`, protected, and not gateway-exposed. Booking implements `POST /api/v1/internal/availability/occupancy`; it returns all requested rooms and finite half-open occupied intervals, including Booking's release buffer. Scheduling requires a complete snapshot no older than 30 seconds. The outbox event contract is notification/invalidation only; Scheduling does not consume or use events as an availability authority.
- All Scheduling business routes under `/api/v1/**`, including `OPTIONS`, are bearer-protected by the service authorization interceptor and delegated to Identity (GET and explicitly read-only operations use `READ`; mutations and unsupported methods use `MANAGE`). Identity resolves the actor from the forwarded bearer token: active users may read, and current system administrators may manage. Scheduling accepts no caller-supplied actor, role, permission, or scope. Missing credentials, Identity denial, and Identity unavailability fail closed.
- Scheduling's versioned routes are service-hosted for authenticated direct access and caller-token-propagating service integrations; they are not routed through the API Gateway or otherwise designated public in Stage 5. The Gateway currently has no Scheduling route; publication/routing remains a Stage 11 responsibility. OpenAPI bearer declarations describe the contract and do not publish a route. The repository contains no Scheduling deployment/ingress policy, so production network reachability must also be restricted by deployment configuration.
- Candidate-producing searches use Booking's implemented protected occupancy provider and return `503 BOOKING_OCCUPANCY_UNAVAILABLE` (or another stable authorization error) rather than treating missing occupancy as an empty set. Stale or incomplete snapshots fail closed. An empty candidate result can be returned without an occupancy call and explicitly marks occupancy as not included.
- Cross-service references are UUIDs and cross-service checks use APIs/events only. No cross-service database foreign keys or duplicated occupancy persistence.
- Keep operational calendar data dynamic; do not hard-code or silently seed working windows or holidays.
- Any required ERD, public API, authorization, service-boundary, or business-rule change must be proposed and explicitly approved before editing the requirements or ERD.
- Work one S5 requirement at a time and pass its focused test, Identity regression, and full-reactor gate before proceeding.

The following Scheduling business routes are implemented on the service for authenticated direct access and authorized caller-token delegation; they are not exposed through public or API Gateway routing in Stage 5. S5-02 provides `GET/POST /api/v1/working-calendars`, `GET/PUT/DELETE /api/v1/working-calendars/{calendarId}`, and `GET/POST /api/v1/working-calendars/{calendarId}/working-day-windows` plus `PUT/DELETE` for a window ID. All operations require a bearer token; active users may read and Identity system administrators may mutate. S5-03 provides GET/POST collection and GET/PUT/DELETE resource operations under `/api/v1/holidays` and `/api/v1/closure-periods`. Holiday scope is calendar, building, their intersection, or nationwide when both IDs are null; Holiday `createdByUserId` is derived from Identity. Closure scope is building or nationwide, with finite `[startsAt, endsAt)` ranges. Both resources preserve active/blocking fields where represented by the ERD, and duplicate holidays for the same exact scope/date conflict. S5-04 provides protected recurrence-rule CRUD and deterministic occurrence-date evaluation under `/api/v1/recurrence-rules`; it accepts bounded date-based RRULEs and returns at most 365 dates through the inclusive one-year horizon in the rule's IANA timezone. S5-05 provides the read-authorized `POST /api/v1/scheduling-constraints/validate` decision API. It maps input Instants into the selected calendar's IANA timezone, requires start and end on the same local date, and, for recurrence, reuses those local times on each stored RRULE date. It checks every occurrence against working windows, active blocking holidays applicable to its calendar/building/nationwide scope, and overlapping building/nationwide blocking closures. A policy conflict returns HTTP 200 with `valid:false` and occurrence-scoped violations; malformed input, missing calendar/rule, timezone mismatch, and Identity authorization failure return errors so callers must not proceed. Nonexistent recurring local times at timezone transitions are rejected. S5-06 provides the read-authorized `POST /api/v1/availability/search` API. It combines Scheduling's bounded calendar, holiday, closure, and optional recurrence data with Room's owner APIs for available status, current room/building rules, working facilities, and maintenance. It returns continuous per-occurrence candidate intervals, not confirmation or a full-series recurrence guarantee. Before returning any non-empty set, it requires a complete, fresh (at most 30 seconds) `v1` Booking occupancy snapshot for every candidate room and subtracts its finite half-open occupied ranges, including Booking's release buffer. Search range and returned-window limits are 31 days and 5,000 respectively; overflow fails rather than truncates. At original S5 acceptance, the internal Booking endpoint was not yet implemented, so candidate-producing searches failed closed with `503 BOOKING_OCCUPANCY_UNAVAILABLE`. S6-13 now provides that protected endpoint; candidate-producing searches continue to fail closed on missing, stale, malformed, incomplete, unauthorized, or unavailable data. Empty candidate sets may return without an occupancy call and explicitly state occupancy was not included. Booking remains responsible for full-series validation and the authoritative concurrent conflict barrier. No S5 requirement writes or persists occupancy.

#### S7-05 template administration, rendering, and audit

Notification templates are immutable versions uniquely identified by `(code, version, channel)`. New versions are inactive. Activating a version takes a PostgreSQL transaction-scoped advisory lock for its code/channel family, deactivates the prior active version, and activates the selected version atomically. The implemented in-app lookup convention is `template.code = event.eventType`; no alternative event-to-template mapping is assumed. Template syntax accepts `{{variableName}}` placeholders, and rendering fails when a placeholder is malformed or its safe event fact is unavailable. Body substitutions are HTML-escaped; subject substitutions have line breaks removed. The renderer uses only the explicit safe-display fact allowlist. Missing active templates and invalid/incompatible templates fail event processing for broker retry/dead-letter handling; no generic or fabricated fallback content is created. `EMAIL` versions require a subject and S7-06 renders them into durable EMAIL delivery rows when a recipient's email preference is enabled.

The bearer-protected Notification template API is `GET /api/v1/internal/notification-templates`, `POST /api/v1/internal/notification-templates`, and `PATCH /api/v1/internal/notification-templates/{templateId}/activation`. Every operation asks Identity to authorize the active caller. Identity permits only an active global `SUPER_ADMIN` with the explicit `NOTIFICATION_TEMPLATE_MANAGE` permission; role/permission values from the caller are not trusted. Create accepts code, positive version, channel, optional subject, and body template, and always creates an inactive version. Activation accepts an explicit boolean. Responses use the shared `ApiResponse` envelope and validation/domain errors use the shared `ApiError` envelope. These are service APIs, not Gateway routes.

Template creation, activation, and deactivation write a safe audit event into Notification's approved `notification_audit_outbox` in the same transaction as the template change. Audit metadata contains code, version, channel, and changed field names, never subject/body content. The relay publishes persistent messages on `audit.notification` only after commit and records publication only after broker confirmation and routing success; failed sends remain pending with bounded exponential delay. Audit Service validates the strict event schema, persists idempotently in its own `AUDIT_EVENT` store, and dead-letters poison/unsupported messages. Actor IDs remain identifiers; neither service reads the other's database. The approved ERD includes this outbox addition and Flyway V4 implements it. Identity Flyway V3 adds only the permission catalog entry; permission assignment remains an explicit Identity administration decision.

#### S7-06 asynchronous email delivery

Email-enabled events and reminders create durable `EMAIL` notification rows using the selected active `EMAIL` template and the recipient's saved channel preference. A scheduled worker claims pending email rows with a PostgreSQL `FOR UPDATE SKIP LOCKED` row lock, resolves the active recipient's stored address through Identity's hidden `POST /api/v1/internal/notifications/delivery-contact` endpoint, and sends via the vendor-neutral Spring SMTP adapter. Identity returns only the account's stored address for an active account; the short-lived Notification service JWT carries only the dedicated `notification:delivery-contact-resolution` permission for this call. No email/display override is accepted from callers or event payloads, and no cross-service database access or Gateway route is introduced.

Flyway V5 adds Notification-owned `delivery_attempt` fields already present in the approved ERD: notification FK, attempt number, result, provider message ID, redacted failure reason, and attempted timestamp. A successful send marks the EMAIL notification `SENT`; retryable failures remain durably scheduled, while permanent or exhausted failures are `DEAD_LETTER`. Attempts persist a generic failure code without SMTP exception details, credentials, recipient address, or message content. Generic SMTP does not provide a standard provider message ID, so that field remains null unless an adapter can supply one. SMTP delivery is asynchronous and outside Booking/Room/Scheduling request processing; a provider outage cannot roll back those source transactions. SMTP is an external side effect and exactly-once delivery is not claimed.

Email is off by default. `NOTIFICATION_EMAIL_ENABLED` must remain false until RRA supplies the approved SMTP-compatible relay and organization-controlled sender. #### S7-07 bounded retry, dead-letter, redrive, and operations

Email delivery uses a bounded five-attempt cycle: the initial attempt plus four retries after 1, 2, 4, and 8 minutes. SMTP 4xx responses and temporary network/provider errors are retryable. SMTP 5xx responses, invalid recipients, and invalid sender/configuration are permanent by default; only explicitly configured provider-documented 5xx response codes may retry. The validated settings are `NOTIFICATION_EMAIL_RETRY_MAXIMUM_ATTEMPTS`, `NOTIFICATION_EMAIL_RETRY_INITIAL_DELAY_MS`, `NOTIFICATION_EMAIL_RETRY_MULTIPLIER`, `NOTIFICATION_EMAIL_RETRY_MAXIMUM_DELAY_MS`, and optional `NOTIFICATION_SMTP_RETRYABLE_RESPONSE_CODES`. Retry-waiting EMAIL rows use the existing `SCHEDULED` status and `scheduled_at`; attempts remain durable in `delivery_attempt`. Permanent and exhausted failures transition to `DEAD_LETTER`. This is separate from in-app notification state and does not change the source booking/room/scheduling transaction.

The user approved `NOTIFICATION_DELIVERY_REDRIVE` and Flyway V6 implements it with exactly the approved columns and uniqueness rule: UUID primary key, notification FK, idempotency key (maximum 128 characters), actor user ID without a cross-service FK, requested timestamp, and unique `(notification_id,idempotency_key)`. A redrive is allowed only for a currently dead-lettered email and restarts the bounded attempt cycle on the same notification; it never creates another notification. Replaying a request with the same key returns the existing result. Concurrent redrive attempts are serialized and conflicting lifecycle states are rejected.

Bearer-protected service-only operations are `GET /api/v1/internal/notification-delivery/health`, `GET /api/v1/internal/notification-delivery/dead-letters`, `GET /api/v1/internal/notification-delivery/dead-letters/{notificationId}`, and `POST /api/v1/internal/notification-delivery/dead-letters/{notificationId}/redrive` with `Idempotency-Key`. Identity authorizes every operation through its internal notification-delivery decision; only an active global Super Admin with the explicit `NOTIFICATION_DELIVERY_MANAGE` permission is allowed. Flyway V4 catalogs the permission but does not assign it automatically. These APIs are not exposed through the API Gateway.

Health reports aggregate queue depth, oldest queued creation time, retries, dead-letter count, delivery successes/failures, and latency count/average/maximum; it does not include recipients or message payload. Dead-letter inspection omits recipient IDs and content, returning sanitized attempt outcomes/failure codes and redrive history. Durable database aggregates back queue/status/outcome counts; latency samples use the process-local Micrometer timer and therefore reset on process restart. Provider message IDs are retained when supplied by the adapter.

## Stage 1: Backend foundation

This repository contains the Stage 1 multi-service backend foundation for the RRA RoomIQ platform. Shared HTTP, validation, logging, OpenAPI, and service bootstrap conventions are implemented in `common-web` and consumed by every service module.

## Current implementation

- Shared standards: common-web
- Service baseline: identity-service plus eight runnable service modules
- Runtime: Java 25, Spring Boot 4.1.1, Spring Framework 7
- Persistence: PostgreSQL + JPA + Flyway
- Security: Spring Security
- Monitoring: Spring Boot Actuator
- Test baseline: Maven test execution using the service's application context smoke test

## Shared backend conventions

- `common-web` provides `ApiResponse<T>`, `ApiError`, and `ValidationError`.
- `GlobalExceptionHandler` standardizes validation and unexpected-error responses.
- `CorrelationIdFilter` accepts or creates `X-Correlation-ID` and propagates it through MDC and response headers.
- Shared OpenAPI metadata is auto-configured for every service.
- Shared `logback-spring.xml` emits correlation IDs in the console pattern.
- Every service has a Spring Boot entry point, Actuator health endpoints, runtime configuration, Maven packaging, and a context smoke test.
- Domain request DTOs must remain inside their owning service and use Jakarta Bean Validation at controller boundaries.

## Target service structure

The backend is intended to evolve into the following service layout under backend/:

- api-gateway
- common-web
- identity-service
- organization-service
- room-service
- scheduling-service
- booking-service
- notification-service
- audit-service
- analytics-service
- infrastructure
- docs

## Design principles

- Each service owns its own domain and data boundary.
- No cross-service DB access or entity sharing.
- APIs are versioned under /api/v1.
- DTOs are used at API boundaries.
- Spring Security controls authorization.
- Business rules belong in the service layer.
- PostgreSQL is authoritative for persistent business data.
- RabbitMQ and Redis support asynchronous workflows and operational coordination.

## Environment conventions

- Local environment configuration is externalized through .env files.
- Do not commit real secrets.
- Use placeholder values in example files.
