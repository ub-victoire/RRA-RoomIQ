# Backend Architecture Baseline

## Target architecture

The backend is designed around independent service ownership and a shared API entry pattern.

## Core principles

- Microservices boundaries are based on business ownership.
- Service-to-service communication happens through HTTP or asynchronous events.
- Scheduling business routes are guarded by service-side bearer validation and Identity authorization. Callers propagate an Identity-issued user token; the actor and permissions are resolved by Identity, not supplied by a caller. Scheduling has no API Gateway route in Stage 5; production deployments must keep the service endpoint and its OpenAPI surfaces on a private/trusted network.
- Scheduling owns calendar rules and availability calculations; confirmed reservation occupancy and its authoritative overlap barrier belong to Booking Service.
- The identity service is authoritative for auth, roles, permissions, scopes, and privilege evaluation.
- Database ownership is maintained per service.

## Booking reservation lifecycle

Booking's protected reservation lifecycle routes are `POST /api/v1/reservations/{reservationId}/check-in`, `/complete`, and `/release`. Identity authorizes the active organizer only within current department/building scope, a lifecycle manager within assigned building scope, or a global system administrator. Booking locks the persisted reservation and permits `CONFIRMED → IN_PROGRESS → COMPLETED`, or explicit `CONFIRMED`/`IN_PROGRESS → RELEASED`; completion and release are terminal outcomes, as are cancellation and release. Actor identity and timestamps are server-derived. Explicit release deactivates every occurrence's occupancy and emits a `MeetingReleased` outbox event atomically. The explicitly approved ERD field `reservation.completed_at` is required exactly when status is `COMPLETED`, enforced in Flyway V3. Occupancy remains a half-open interval with release buffer and database exclusion constraints. No automatic missed-check-in or overdue release runs, and no Gateway route is configured.

## S6-12 retry semantics

Transaction-scoped PostgreSQL advisory locks serialize request/direct-booking, extension, and share-link creation retries before idempotency lookup; existing database uniqueness constraints remain the integrity barrier. Equivalent calls replay existing resources, while reuse with changed payloads returns explicit conflict errors. Cancellation replay requires the same currently authorized actor and equivalent reason/override data. Share-link create requires `Idempotency-Key`; versioned HMAC derivation reproduces the original token on replay while only its hash is stored. The only S6-12 schema addition approved by the user is nullable `MEETING_SHARE_LINK.idempotency_key VARCHAR(128)` with `UNIQUE(created_by_user_id, idempotency_key)`, implemented by Flyway V6.

## S7-01 notification event consumer

Notification Service consumes version-1 messages from the durable `roomiq.events.v1` exchange. It validates event type/source/aggregate/routing-key agreement, envelope and payload facts, UUIDs, timestamps, recipient IDs, and rejects email/display-name overrides. A PostgreSQL `notification_event_receipt` row and all resulting in-app notification rows commit in one transaction; unique `event_id` insertion makes matching duplicate delivery a no-op, and conflicting envelope metadata is rejected. RabbitMQ automatic acknowledgement occurs only after the transactional service returns; bounded retries route exhausted or poison messages to a durable dead-letter queue. The `NOTIFICATION_EVENT_RECEIPT` addition was explicitly approved by the user.

Booking emits request, decision, cancellation, extension, completion, explicit release, and reminder events from its existing transactional outbox. Request events use version 2 routing context: Secretary requests are explicitly marked `SCOPED_ADMIN_REQUEST` without an embedded Admin audience, direct bookings use `NONE`, and extension requests are marked `SCOPED_ADMIN_REQUEST`. Decision events identify the persisted requester and include the decision comment when supplied. Explicit release is protected by current Identity lifecycle authorization and releases active reservation occurrences transactionally. Although completion and release producer events carry Booking-owned organizer/participant identifiers, Notification currently persists only their receipt and suppresses notice creation until an explicit recipient policy is approved. Automatic-release/no-show likewise has receipt-only behavior; no automatic overdue release exists. Each confirmed occurrence emits an organizer-only reminder at 15 and 5 minutes before its validated start instant, preserving the validated IANA timezone and reservation reference in the event. Notification stores reminders durably as `SCHEDULED`, releases them as `PENDING` only when due after checking terminal-event receipts under a reservation-scoped advisory lock, and prevents duplicate schedules. Cancellation, completion, release, and automatic-release events cancel future/unread reminder records; a late schedule event after a terminal receipt is ignored. Room writes status and maintenance events to the user-approved `ROOM_EVENT_OUTBOX`; before that write it calls Booking's protected `POST /api/v1/internal/notifications/room-event-recipients`, which uses Identity `ROOM_MANAGE` authorization and returns organizers/internal participants for active overlapping reservation occurrences. Maintenance recipients overlap the maintenance range; status recipients overlap from the status-change instant onward. Room events use aggregate type `ROOM`. Booking, Room, and Notification support per-service RabbitMQ credentials in configuration, but production credentials and routing-key ACLs are not provisioned or verified here. No Notification business route is added to the API Gateway.

## S7-02 recipient routing

Notification resolves request/extension Admin audiences through Identity's hidden `POST /api/v1/internal/notifications/recipient-resolution` endpoint, without a caller JWT or a cross-service database read. The call uses a distinct short-lived RS256 service JWT (`sub=notification-service`, configured issuer/audience, UUID `jti`, `notification:recipient-resolution` permission, and `kid`-selected key). The private signing key is mounted only in Notification; Identity receives the matching current/optional previous public key. Identity validates the service token and versioned Booking context, confirms the current active Secretary and current scoped request/extension permission, derives the office-building scope from Identity-owned user data, and returns only active building-scoped Admin IDs. No building scope or recipient list is accepted from the service caller. Notification propagates the event's correlation ID as `X-Correlation-ID` and persists correlation/causation on the durable receipt.

Legacy version-1 request events are acknowledged with receipts but no guessed Admin notifications. Version-2 direct bookings explicitly request no Admin routing. Decisions route to the Booking-owned requester UUID and retain the decision comment in an explicit safe-display allowlist. Cancellation and room-conflict/maintenance recipients are identifiers derived from service-owned Booking/Room facts; event payloads cannot override email or display names. Reminder recipients remain organizer-only. Meeting completion, explicit release, and automatic-release/no-show are durable receipt-only events with no notification rows until their recipient configuration is separately approved. Their terminal state still suppresses/cancels pending reminders. Notification Service never accesses another service's database, no Notification routes are Gateway-exposed, and no ERD or Flyway migration was changed for S7-02.

The in-app inbox uses `GET /api/v1/notifications` with optional event type, status, and read-state filters plus bounded pagination and allowlisted sorting; the corresponding `PATCH /api/v1/notifications/{notificationId}/read` is owner-scoped and atomic. Both endpoints forward the caller bearer token to Identity's existing protected `AUTHENTICATE` authorization action, so the active session/account and recipient UUID are verified by Identity for each request. Responses use the shared API envelope and expose only allowlisted display payload fields; existing `NOTIFICATION` ERD fields and Flyway schema already cover inbox state and references.

S7-04 preferences are persisted in Notification-owned `user_notification_preference` using the approved ERD fields and unique `(user_id,event_type)` key (Flyway V3); `user_id` remains an Identity identifier, with no cross-service database access or FK. Protected `GET /api/v1/me/notification-preferences` and `PUT /api/v1/me/notification-preferences/{eventType}` derive the owner through Identity's active-session `AUTHENTICATE` action. Missing rows default to in-app enabled/email disabled; saved flags are independent with no non-disableable event types. Event processing applies the in-app flag and due reminder delivery rechecks it before making the reminder available. S7-06 uses the email flag to gate durable EMAIL notification creation; sending remains disabled by default until production relay/sender values are configured.

## S7-05 versioned templates and audited administration

Notification stores immutable template versions by `(code, version, channel)`; create always starts inactive, and a PostgreSQL advisory lock serializes active-version replacement per code/channel. In-app event lookup uses the explicit code convention `template.code = event.eventType`. Only `{{variableName}}` placeholders from the safe display-fact allowlist render; malformed syntax, unavailable values, or missing active templates fail processing instead of generating fallback content. Body substitutions are HTML-escaped and subject line breaks are removed. `EMAIL` templates require a subject and are rendered into durable EMAIL rows by S7-06 when email preference is enabled.

`GET`/`POST /api/v1/internal/notification-templates` and `PATCH /api/v1/internal/notification-templates/{templateId}/activation` require an active global Super Admin with Identity's explicit `NOTIFICATION_TEMPLATE_MANAGE` permission. Notification authorizes each operation through Identity using the caller bearer token; these APIs are not Gateway-routed. Template mutation and a safe audit event are committed together to the approved Notification-owned audit outbox; audit payloads omit subject/body content. The confirmed outbox relay publishes `audit.notification`; Audit Service validates and idempotently persists the event in its own `AUDIT_EVENT` store, with poison-message dead-lettering. The approved ERD addition and Flyway V4 are aligned; Identity Flyway V3 adds only the permission catalog entry.

## S7-06 asynchronous email delivery

Email-enabled events/reminders create durable EMAIL rows from active EMAIL templates and per-user preference. A scheduled worker claims pending rows with `FOR UPDATE SKIP LOCKED`, resolves the active user's stored email through Identity's hidden `POST /api/v1/internal/notifications/delivery-contact`, then sends via the vendor-neutral Spring SMTP adapter. The internal Identity call requires a short-lived service JWT with only `notification:delivery-contact-resolution`; Notification does not store the email, trust event/contact overrides, access another service database, or add a Gateway route.

Flyway V5 creates `delivery_attempt` with the exact fields already present in the approved ERD. Outcomes persist attempt number, status/result, attempted time, optional provider message ID, and a generic redacted failure reason. Success marks the notification `SENT`; retryable failures remain `SCHEDULED`, and permanent/exhausted failures are `DEAD_LETTER`. SMTP exception text and personal data are not persisted. A generic SMTP relay has no standard provider message ID, so the field is null unless the adapter receives one. SMTP is asynchronous and cannot roll back core Booking, Room, or Scheduling transactions; exactly-once delivery is not claimed.

`NOTIFICATION_EMAIL_ENABLED` defaults to false. Production delivery remains off until RRA provides the approved SMTP-compatible relay endpoint, secret credentials, and organization-controlled sender address/name. All host/port/auth/TLS/timeout/sender values are deployment-injected; STARTTLS is required by default, and implicit TLS settings must be consistent. The existing approved ERD was not changed.

## S7-07 email retry and operations

The approved retry cycle allows five total attempts with delays of 1, 2, 4, and 8 minutes. SMTP 4xx and temporary network/provider failures retry. SMTP 5xx, invalid recipients, and invalid sender/configuration are permanent unless an explicitly configured provider-documented temporary SMTP response code applies. Waiting retries use the existing `SCHEDULED`/`scheduled_at` state; permanent or exhausted deliveries transition to `DEAD_LETTER`. Attempts remain separately persisted in `delivery_attempt`, and SMTP delivery remains outside all source booking/room/scheduling transactions.

The user-approved `NOTIFICATION_DELIVERY_REDRIVE` table is implemented in Notification Flyway V6. It stores a notification ID, idempotency key (128 characters maximum), actor user ID without a cross-service FK, and request time, with uniqueness on `(notification_id,idempotency_key)`. Redrive reuses the dead-lettered EMAIL notification and starts a fresh bounded attempt cycle; duplicate notification/key calls replay the prior operation. Protected operational endpoints expose aggregate health, paginated dead-letter summaries, sanitized attempt/redrive history, and redrive. Identity permits them only to an active global Super Admin with the dedicated `NOTIFICATION_DELIVERY_MANAGE` permission; Identity Flyway V4 catalogs the permission but does not assign it. Responses omit recipient identifiers and message content. Latency metrics are process-local Micrometer timer samples; durable database aggregates back queue and delivery outcome counts. These service routes are not Gateway-routed.

### S6-08 meeting visibility and participant ownership

Booking owns its Meeting and MeetingParticipant records and the one-to-one Reservation/Meeting constraint. For each read or mutation, Booking loads the persisted reservation and booking request, verifies requester/organizer, room, building, and department facts are consistent, and forwards the caller bearer token to Identity. Identity rechecks the current active account and scope: PRIVATE allows the organizer or a scoped Booking reviewer; INTERNAL adds active users currently assigned to the meeting building. The `PUBLIC` enum value does not make protected meeting endpoints public; a separate share-link endpoint returns only its explicit public-card fields. Participant additions cannot set actor, organizer role, or invite status. Internal account names come from Identity and must be active in the same building; external participant email/name is validated and an external participant is accepted only if the persisted booking request's Room-policy-validated `externalGuests` flag is true. Meeting-row locking serializes additions and removals to enforce duplicate checks without changing the approved ERD. Meeting/participant routes are not Gateway-routed.

### S6-13 occupancy provider and transactional event outbox (complete)

Booking implements protected `POST /api/v1/internal/availability/occupancy` v1 for Scheduling. It queries active Booking-owned occurrence ranges overlapping the requested half-open range, returns the full finite stored occupied interval (already including the release buffer), and includes every requested room exactly once, even if that room has no occupancy. The route uses the global Identity-backed `/api/v1/**` bearer guard, is hidden from generated public OpenAPI, and is not configured on the Gateway. Invalid input and data-access failures fail closed; Scheduling additionally enforces its 30-second freshness and completeness requirements.

Booking also writes versioned `booking.occupancy.changed` events to the user-approved `BOOKING_EVENT_OUTBOX` within the same database transaction as confirmation, cancellation, or extension occupancy changes. Flyway V7 adds that table and the ERD is synchronized. A scheduled relay claims committed rows with `FOR UPDATE SKIP LOCKED`, publishes to the durable `roomiq.events.v1` exchange, requires correlated positive publisher confirmation with no mandatory return, and persists capped retry/backoff state on failure. Delivery is at-least-once; consumers deduplicate by `eventId` and ignore only strictly older reservation versions (distinct recurring occurrence events can share a version). Scheduling currently has no event consumer and continues to rely on its fresh synchronous occupancy snapshot as authoritative. Focused outbox/transaction tests passed 20/20; the Booking suite passed 138/138, Identity 53/53, common-web 6/6, and the full 11-module backend reactor passed 311/311, with zero failures, errors, or skips.
